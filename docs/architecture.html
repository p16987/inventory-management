Architecture reference

Factory Inventory Management System

A Vue 3 single-page app talking to a single-module FastAPI service that serves seven JSON files held in memory. No database, no build step on the server, no authentication.

Frontend :3000 Backend :8001 14 GET endpoints 0 write endpoints ~7,500 lines of Vue 309 lines of FastAPI

01 — Shape

Two processes and a folder of JSON

The whole system is three moving parts. Vite serves the compiled SPA on port 3000. Uvicorn serves FastAPI on port 8001. At import time, server/mock_data.py reads seven JSON files from server/data/ into module-level Python lists, and every request filters those lists in memory.

There is no dev proxy in client/vite.config.js, so the browser calls the API cross-origin at a hardcoded http://localhost:8001/api. The backend answers with allow_origins=["*"].

03 — Data flow

What happens when someone changes a filter

The four filters in the header bar are the spine of the app. Their state lives in module-level refs inside useFilters.js, which makes the composable a singleton: every view imports the same refs, so one dropdown change fans out to all mounted views. Each view owns a watcher that refetches, and six of the seven views have one.

Which filters reach which endpoint

/api/inventoryyesyes—— (no date field)

Matching is not uniform: warehouse is compared exactly and case-sensitively, while category and status are lowercased on both sides. Month matching is a substring test against order_date, with a QUARTER_MAP covering Q1–Q4 of 2025 only — an unrecognised quarter falls through and returns everything unfiltered.

04 — Frontend

Six routes, three singletons

Views hold raw API rows in refs and derive every displayed number in a computed property. There is no charting dependency anywhere in the project, and only one real SVG chart: the dashboard's order-status donut. Every other "chart" is a stack of divs with percentage widths or pixel heights, scaled by a per-view helper. The other two dozen inline SVGs are icons.

Shared state

  • useFilters.js — the four filter refs plus getCurrentFilters(), which renames location to warehouse and period to month for the API.
  • useI18n.js — English and Japanese dictionaries, locale persisted in localStorage, with English as the per-key fallback. Currency follows the locale: en shows USD, ja converts at a fixed rate of 150 yen to the dollar in utils/currency.js.
  • useAuth.js — a hardcoded profile and task list that change name and language with the locale. There is no login, token or session anywhere in the system.

Components

App.vue is the shell: nav tabs, the global FilterBar, profile menu, and the task modal wiring. The other eight components are detail modals and menus — TasksModal is the largest at 621 lines.

05 — Backend

One module, fourteen read-only routes

Everything is in server/main.py: two filter helpers, six Pydantic models, and the routes. Six of the fourteen endpoints declare a response_model; the rest return plain dicts and lists that bypass validation on the way out.

Aggregation is split three ways, which is the main thing to know before changing a number: some totals are pre-computed in spending.json, some are calculated in Python per request, and the rest are computed client-side from raw rows. The dashboard, for instance, receives its five figures from the API but recalculates its charts from the same 250 orders in the browser.

06 — Loose ends

Gaps worth knowing before you change anything

These are things I verified in the code or against the running servers, not style opinions.

  • BrokenThe client calls six endpoints that do not exist. api.js defines task CRUD (/api/tasks) and purchase orders (/api/purchase-orders); main.py implements neither. GET /api/tasks returns 404 against the running server. App.vue calls it on mount, logs the error, and falls back to the hardcoded task list.
  • Half-builtPurchase orders are scaffolded but inert. The PurchaseOrder and CreatePurchaseOrderRequest models are never referenced by a route, and purchase_orders.json is an empty array, so has_purchase_order is always false.
  • BrokenThe dashboard renders a component that does not exist. Dashboard.vue:289 uses <PurchaseOrderModal>, which is neither imported nor present in components/. The Create PO and View PO buttons resolve to nothing.
  • BugThe donut arcs are scaled to the wrong circumference. getCircleSegment() multiplies by 440 while the circles use r="65" and a dash total of 408 — the real circumference is 2π·65 ≈ 408.4 — so every segment runs about 8% long and the arcs overlap.
  • Demo dataThree of the five dashboard KPI tiles are hardcoded. Inventory turnover (4.2), order fill rate (96.8%) and average processing time (2.8 days) are literals in Dashboard.vue, not derived from any endpoint. Only the revenue and orders-fulfilled tiles move with the data.
  • UnreachableBacklog.vue has no route. The view loads backlog and inventory data but is not registered in the router and is not imported anywhere, so nothing renders it. Backlog data still reaches the dashboard.
  • InconsistentReports.vue is the outlier in every respect. It is the only view on the Options API, the only one calling axios directly with a hardcoded URL instead of going through api.js, the only one with no i18n, and the only one that ignores the filter bar — which is still displayed above it. Spending is a softer version of the same problem: its watcher body is empty and its getOrders() call passes no filters, so only the period select affects it.
  • BugOne dashboard tile ignores the filters. total_backlog_items counts the global list rather than a filtered one, so it stays at 4 for every warehouse, category and month. In the same response, total_inventory_value is rounded but total_orders_value is not.
  • MismatchTwo datasets that cannot be joined. Inventory and orders use city warehouses (London, San Francisco, Tokyo) and electronics categories; transactions use warehouses A, B, C with categories like Widgets and Labor. It never surfaces because the spending endpoints take no filters.
  • Stalegenerate_data.py would break the app. It regenerates orders.json with the old A/B/C warehouse scheme, runs on import with no __main__ guard, writes to a relative path, and sets no random seed.
  • Docs driftThe test suite is smaller than advertised. 40 tests exist across three files. tests/README.md and TEST_SUMMARY.md both describe a test_orders.py with 15 tests and claim 55 total; that file is not in the repo, so orders, both report endpoints, and the quarter logic are untested.

07 — Running it

Two commands, or one script

./scripts/start.sh starts both servers, logging to /tmp/inventory-backend.log and /tmp/inventory-frontend.log, and ./scripts/stop.sh stops them by PID file, falling back to whatever holds ports 8001 and 3000. Started by hand it is uv run python main.py in server/ and npm run dev in client/. Interactive API docs come free at localhost:8001/docs. Tests run from tests/ with uv run pytest.

Written from the code in this working copy on 17 September 2026 — version numbers are what is installed in client/node_modules and server/.venv. Endpoint behaviour was checked against the servers running on ports 3000 and 8001.
